## Architecture

**Stack:** React 19 + TypeScript + Vite + Chakra UI v3 + React Router v7, with Supabase (Auth / Postgres / Storage) as the backend.

**Entry point:** `src/main.tsx` wraps the app in `BrowserRouter` → `Provider` (Chakra UI + color mode) → `AuthProvider` → `App` + `Toaster`.

**Routing — two-level structure:**
- `src/router/Router.tsx`: top-level. `/` → Login, `/signup` → Signup, `/share/:token` → `SharedMeals` (the public read-only share page; outside `PrivateRoute`, no login, no `Header`). `/*` → `HomeRouter` wrapped in `PrivateRoute`. Catches 404.
- `src/router/PrivateRoute.tsx`: shows a spinner while auth is loading, redirects to `/` when there is no user.
- `vercel.json` rewrites every path to `index.html` so React Router handles deep links. Without it, opening `/dashboard` or a share link directly returns Vercel's 404.
- `src/router/HomeRouter.tsx`: authenticated area. Renders `<Header>` persistently, then nested routes (`/dashboard`, `/list`, `/profile`).

**Path alias:** `@/` maps to `src/` (configured via `tsconfigPaths` in Vite and `tsconfig.app.json`). Use `@/` for every import — including same-folder files, tests importing the file under test, and CSS — never relative `./` or `../` paths.

### Supabase

- Client is created in `src/lib/supabase.ts` from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (`.env`). When they are not set, `supabase` is `null`, so data-access code starts with `if (!supabase) return`.
- Schema lives in `supabase/migrations/` (`meals` table, `meal-images` storage bucket, `delete_user()` RPC used for account deletion, `meal_shares` table and `get_shared_meals()` RPC for share links). See README for setup and DB reset.
- Share links (sharing meals read-only with e.g. a dietitian):
  - `meal_shares` holds one row per link: `token` (64-char hex, generated by the DB), `label` (who it is for), `start_date` / `end_date` (range of `meals.eaten_at` to show; `end_date` null = keep sharing new meals), `expires_at` (when the link stops opening), `revoked_at`, `include_memo` / `include_images`. RLS lets only the owner read/insert/update, and column grants restrict the client: insert only `label, start_date, end_date, expires_at, include_memo, include_images` (never send `user_id` or `token` — it fails with a permission error), update only `revoked_at`. Links are revoked, never deleted.
  - The share page reads data only through `get_shared_meals(p_token)` (`security definer`, executable by `anon`); `meals` RLS is unchanged. It returns `{ status: "not_found" }`, `{ status: "expired" }` (expired or revoked), or `status: "ok"` with the owner's name/goal, the share settings and `meals` (`MealSummary` shape; `memo` / `image_path` are null when not shared; no `user_id` or email).
  - Images stay in the public `meal-images` bucket, so a shared photo URL works for anyone who has it (moving to a private bucket is tracked separately).
- Auth state: `AuthProvider` (`src/contexts/AuthContext.tsx`) subscribes to `onAuthStateChange`; read it with `useAuth()` (`src/hooks/useAuth.ts`) → `{ user, session, loading, signIn, signUp, signOut }`. Profile data (display name, goals) is stored in `user.user_metadata` (`full_name`, `goal_type`, `goal_detail`).
- Meal data is held per page by `useMeals`, so a save made elsewhere (e.g. the Header's add-meal modal) must announce itself: `src/lib/mealEvents.ts` provides `notifyMealsChanged()` / `subscribeMealsChanged()`. `useSaveMeal` notifies on success and every mounted `useMeals` refetches. Pages do not need to call `refresh()` after closing `MealFormModal`.
- Meal images: helpers in `src/utils/imageUpload.ts` (`uploadMealImage`, `deleteMealImage`, `getMealImageUrl`).

### Directory layout

- `src/pages/` — one file per route. Pages compose section components and own only page-level state (modals, filters, pagination). Each page is a named export wrapped in `memo`.
- `src/pages/SharedMeals.tsx` — the public share page (`/share/:token`). Fetches with `useSharedMeals`, shows a notice for `not_found` / `expired` / fetch errors, and sets `<meta name="robots" content="noindex, nofollow">` (React 19 hoists it into `<head>`).
- `src/components/<page>/` — components used by a single page (`dashboard/`, `list/`, `profile/`, `share/`). The one exception is the share page, which reuses `list/MealGroupList` read-only (omit `onEdit` / `onDelete` to hide the buttons) and `dashboard/MealTimeDistributionSection`; keep those two usable without the owner's data.
  - `profile/ShareSection.tsx` — issue/list/revoke share links (owns its form state, uses `useMealShares`). Parts: `ShareLinkItem.tsx` (copy link, Web Share API "送る" when available, revoke), `RevokeShareDialog.tsx`.
  - `share/` — `SharedMealsHeader` (whose records, goal, range, expiry), `SharedMealsSummary` (counts + meal-time distribution), `SharedMealsNotice` (messages when nothing can be shown).
  - In the share UI, "見せる記録" (`start_date` / `end_date`, the range of meal dates) and "リンクを開ける期間" (`expires_at`) are separate settings; keep the wording "いつの食事から / いつの食事まで" vs "リンクを開ける" so the two are not read as the same deadline. Shared wording lives in `src/utils/shareFormat.ts`.
- `src/components/ui/` — shared components:
  - `FormField.tsx` — label + input pair built on Chakra `Field`; the label is linked to the `Input` / `Textarea` inside it. Use it for every labeled form control, except groups of checkboxes: wrap those in Chakra `Fieldset` (`Fieldset.Root` / `Fieldset.Legend` / `Fieldset.HelperText`) instead. Inside a `Field`, every checkbox gets the same id, which breaks their labels (see "見せる内容" in `ShareSection.tsx`).
  - `MealFormModal.tsx` — add/edit meal dialog (used by Dashboard and List). Its parts live in `mealForm/`.
  - `CalendarPicker.tsx` — month calendar for picking a date (`value` / `onChange`).
  - `ChoiceButtonGroup.tsx` — row of buttons for picking one option (`options` / `value` / `onChange`, generic over the value type; `""` = nothing selected). Used for meal time and goal type.
  - `DateField.tsx` — date input: a button showing the date that opens `CalendarPicker` in a Popover (owns its open state).
  - `Pagination.tsx`, `PrimaryButton.tsx`, `MealThumbnail.tsx`, `ImageLightbox.tsx`.
  - `LogoIcon.tsx` — the app mark (a bowl with a sprouting leaf, inline SVG in `currentColor`; size with `boxSize`, color with `color`/`bg`). `public/favicon.svg` draws the same mark, so change both together.
  - `layout/Header.tsx` (sticky nav + mobile Drawer), `layout/AuthLayout.tsx` (Login/Signup frame).
  - `toaster-instance.ts` — import `toaster` from here (not from `toaster.tsx`) to show toasts.
  - Generated Chakra snippets: `provider.tsx`, `color-mode.tsx`, `toaster.tsx`, `tooltip.tsx`.
- `src/hooks/` — `useAuth`, `useMeals` (fetches the user's meals, returns `{ meals, setMeals, loading, refresh }`; refetches automatically when `notifyMealsChanged()` fires), `useDashboardStats` (pure aggregation for the dashboard, relative to today; `countByMealTime(meals)` is the date-independent meal-time count, also used by the share page), `useMealShares` (the user's active share links — not revoked, not expired — with `createShare(values)` resolving to the new `MealShare` or `null`, and `revokeShare(id)` resolving to a boolean; validates and shows toasts), `useSharedMeals(token)` (calls `get_shared_meals`, returns `{ result, loading, error }`; no toasts, since the viewer is not an app user), `useSaveMeal` (validates, uploads the image, inserts/updates a meal, deletes a replaced image, shows toasts; `saveMeal` resolves to `true` on success). If the DB write fails it deletes the image it just uploaded; deleting the old image after a successful update is best-effort and never turns the save into a failure.
- `src/constants/` — `mealTime.ts` (`MEAL_TIME_META` labels/colors/order and `MEAL_TIME_ORDER`; derive meal-time lists from these instead of hard-coding), `auth.ts` (`PASSWORD_MIN_LENGTH`, shared by signup and password change), `date.ts` (`WEEKDAY_LABELS`, indexed by `Date#getDay()`), `meal.ts` (`MEAL_NAME_MAX_LENGTH`, `MEAL_MEMO_MAX_LENGTH`), `goal.ts` (`GOAL_TYPES` / `GoalType`, used by the profile goal form and the share page), `share.ts` (`SHARE_LABEL_MAX_LENGTH`, matching the DB check; `SHARE_EXPIRY_OPTIONS` with string `value`s for `ChoiceButtonGroup` and the number of `days`).
- `src/types/` — `meal.ts` (`Meal`, and `MealSummary`, the fields a list row needs; list components take `MealSummary` so shared meals without `user_id` / `created_at` fit), `mealShare.ts` (`MealShare`, `SharedMeals`, `SharedMealsResult`).
- `src/styles/` — shared style objects (`inputStyle` for form inputs, `cardStyle` for dashboard cards).
- `src/utils/mealValidation.ts` — `validateMealInput(name, memo)`: trims and checks meal input, returns the cleaned values or an error message.
- `src/utils/dateUtils.ts` — `toDateStr` (local `YYYY-MM-DD`; `meals.eaten_at` uses this format and is compared as a string), `fromDateStr` (the reverse, local midnight), display formatters.
- `src/utils/mealList.ts` — `sortMealsForList` (newest date first, then meal-time order) and `groupByDate` (→ `DateGroup[]`), shared by List and the share page.
- `src/utils/shareValidation.ts` (`validateShareInput`), `shareUrl.ts` (`buildShareUrl(token)` → `${origin}/share/${token}`), `shareFormat.ts` (share range / contents / expiry wording).

### Component conventions

- Props are plain values (`fullName`, `email`, `createdAt`), not the Supabase `User` object; the page extracts them from `user`.
- A section that edits data owns its own form state and save handler (e.g. `ProfileEditSection`, `GoalSection`, `PasswordSection`); the page passes only initial values.
- Callbacks passed to `memo` components are wrapped in `useCallback` in the parent.
- Non-component exports from a component file are limited to types (e.g. `GoalType`, `DateGroup`).

### Chakra UI v3 notes

- Uses `defaultSystem` (not a custom theme). Color mode is managed via `next-themes` through the generated `color-mode.tsx` wrapper.
- `variant="filled"` on `Input` does not exist in v3; use `"outline"`, `"subtle"`, or `"flushed"`.
- Use `colorPalette` prop (not `colorScheme`) on buttons and interactive elements.

## Testing

Vitest + Testing Library on jsdom (`src/test/setup.ts` loads `jest-dom`). Tests sit next to the file they cover (`*.test.ts(x)`).

- Mock Supabase and the toaster with `vi.hoisted` + `vi.mock("@/lib/supabase", ...)` / `vi.mock("@/components/ui/toaster-instance", ...)` (see `src/pages/Profile.test.tsx`, `src/hooks/useMeals.test.tsx`). Profile renders `ShareSection`, so a Profile test's Supabase mock must also provide `from(...)` returning an empty list; otherwise fetching share links fails and shows an error toast.
- Components that sit on top of a data hook (`ShareSection`, `SharedMeals`) are tested by mocking the hook module (`vi.mock("@/hooks/useMealShares", ...)`); the hooks themselves are tested against a mocked Supabase query chain (see `src/hooks/useMealShares.test.tsx`).
- Wrap rendered components in `<ChakraProvider value={defaultSystem}>`; provide auth with `<AuthContext.Provider value={...}>`.
- For date-dependent logic, fix the clock with `vi.useFakeTimers({ toFake: ["Date"] })` + `vi.setSystemTime(...)` (see `src/hooks/useDashboardStats.test.ts`).
- jsdom has no `ResizeObserver`; tests that open a Chakra Popover must stub it (see `src/components/ui/DateField.test.tsx`).
- Prefer querying form controls by label (`getByLabelText`) now that labels are linked via `FormField`.

## Known limitations

- `useMeals` fetches all of the user's meals with no paging; Supabase caps a single select at 1000 rows by default, so totals on Dashboard/List become inaccurate past that.
